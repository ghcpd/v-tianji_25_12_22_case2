## High-priority (small, low-risk) tasks — great for first-time contributors

### 1) Fix event-listener lifecycle (memory-leak / incorrect effect) — bug
- Where: App.tsx (the `useEffect` that calls `window.addEventListener('resize', ...)` and `document.addEventListener('click', ...)`).
- Why good: single-file change, high impact (prevents leaks/unexpected behavior), easy to test and review.
- Clarifying questions
  - Should handlers remain simple console-logging, or should they be removed/changed to no-op in production?
  - Any preferred pattern (define handlers inside effect vs. `useCallback`) for consistency with codebase?
- Safe high-level approach
  - Add a cleanup function that removes the listeners.
  - Either define handlers inside the effect or wrap them in `useCallback` and include them in the dependency array to satisfy hooks rules.
  - Remove stray `console.log` calls or gate them behind a debug flag.
- Verification
  - Unit test (or manual): mount/unmount component and assert `removeEventListener` was called (or observe no additional handlers on repeated mounts).
  - Manual: open DevTools → add/remove component (or reload) and confirm no duplicate logs on resize/click.
- Estimate: 1–2 hours, ~10–25 LOC change
- Suggested labels: bug, good first issue

---

### 2) Replace deprecated `onKeyPress` with accessible keyboard handling
- Where: App.tsx — input uses `onKeyPress` to detect Enter.
- Why good: small change, accessibility + correctness improvement.
- Clarifying questions
  - Should Enter be the only key handling required? Any additional keyboard shortcuts expected?
- Safe high-level approach
  - Replace `onKeyPress` with `onKeyDown` (check `e.key === 'Enter'`) and add an accessible `<label>` for the input (or `aria-label`).
  - Add a unit test that simulates Enter key to add a todo.
- Verification
  - Keyboard test: pressing Enter adds a todo.
  - Accessibility: input is focusable and has an accessible name.
- Estimate: 30–60 minutes, ~5–15 LOC
- Suggested labels: enhancement, accessibility, good first issue

---

### 3) Add defensive localStorage parsing + schema validation
- Where: App.tsx — `JSON.parse(localStorage.getItem('todos'))` (no try/catch or validation).
- Why good: prevents runtime crashes from corrupted data; small, high-value change.
- Clarifying questions
  - Do we need to support older schema versions or migrations?
  - Is silent failure acceptable (ignore invalid data) or should the app surface a warning?
- Safe high-level approach
  - Wrap parse in `try/catch`; validate parsed object is an array of todos with required fields before calling `setTodos`.
  - Optionally add a migration step or a safe fallback to `[]`.
  - Add unit tests for corrupted / unexpected localStorage values.
- Verification
  - Simulate `localStorage` containing invalid JSON and ensure app loads without throwing.
- Estimate: 1–2 hours, ~10–30 LOC
- Suggested labels: bug, robustness

## UX / Accessibility tasks — quick wins

### 4) Add visible label + ARIA to interactive controls (input, filter buttons, delete button)
- Where: App.tsx, App.css
- Why good: broad accessibility impact, trivial code changes.
- Clarifying questions
  - Prefer visible label text or visually-hidden label pattern?
  - Any copy preferences for button `aria-label`s (e.g., “Delete todo: <text>”)?
- Safe high-level approach
  - Add `<label htmlFor="todo-input">` OR `aria-label="Add todo"`.
  - Add `aria-pressed` / `aria-current` to filter buttons when active.
  - Ensure focus styles are visible (add `:focus-visible` CSS).
  - Add one axe/aria unit test (or a simple DOM assertion).
- Verification
  - Axe/Accessibility lint run; keyboard navigation works; screen reader name present.
- Estimate: 1–3 hours, ~10–40 LOC
- Suggested labels: accessibility, good first issue
